To move your app to another database engine, you install that engine's package, introspect the new database and check which dialect `ask()` uses. The rest of AskDB doesn't change. The dialect is the one part that knows your engine's SQL flavor. With a new `dialect` id, the same enrichment workflow and the same `ask()` call work against the new engine.

## What stays the same

- The schema artifact format. Same `schema.json`, same `tables/*.md`, same enrichment workflow.
- The `ask()` API. Same options, same return shape.
- The SQL checks. Every engine's SQL goes through the same checks, and they are heuristics, not a security boundary. See [Safety boundaries](/concepts/safety-boundaries/). The rules:
  - The SQL starts with `SELECT` or `WITH`.
  - It is a single statement (with a SQL Server caveat).
  - It has no comments, no write or DDL keywords, no locking reads and no calls to known side-effecting functions.
  - The heuristic tenant and sensitive-column checks run.

  Only the detail changes for each engine. Each engine splits SQL into tokens the way it reads strings, quoted identifiers and comments. Each engine adds its own entries to the keyword denylist, the function denylist, or both. The locking reads that the check rejects follow each engine's syntax too, such as `LOCK IN SHARE MODE` on MySQL and `WITH (UPDLOCK)` on SQL Server.
- The privacy model. The model sees schema, not rows, regardless of engine.

## What changes

- The engine package you install.
- The dialect. A direct `ask()` call passes it; the CLI and `@askdb/client` infer it from the schema artifact (see [step 3](#3-update-the-dialect-value-in-ask-calls)).
- The dialect's prompt brief. It tells the model the engine's SQL, such as `ILIKE` and `::type` on Postgres, or `TOP` on SQL Server.
- The read-only check's rules for the engine: extra forbidden keywords and blocked functions.
- How the prompt `ask()` sends quotes names. The prompt lists a schema, table or column quoted the engine's way when its name is one of the engine's reserved words. The model then copies it quoted, as the table below shows. Two more rules:
  - **Capitals on Postgres.** Postgres folds unquoted names to lowercase, so a name with capitals is quoted too. A Prisma table `Post` is listed as `public."Post"`.
  - **Qualified names.** Where the prompt lists tables with their schema, it also tells the model to quote each part of a qualified name separately (`"billing"."order"`, not `"billing.order"`).
- The driver your app uses to execute. The matrix below lists the suggested driver for each engine.
- How the CLI introspects the database (connection-string format and catalog queries differ per engine).

## The matrix

| Engine | Engine package | `dialect` value | Suggested driver |
| --- | --- | --- | --- |
| PostgreSQL | `@askdb/postgres` | `"postgres"` | `pg` |
| MySQL | `@askdb/mysql` | `"mysql"` | `mysql2` |
| MariaDB | `@askdb/mysql` | `"mariadb"` | `mysql2` |
| SQLite | `@askdb/sqlite` | `"sqlite"` | `better-sqlite3` |
| SQL Server | `@askdb/sqlserver` | `"sqlserver"` | `mssql` |

| Engine | `introspection.schemas` lists | The reserved word `order` in the prompt | Connection string |
| --- | --- | --- | --- |
| PostgreSQL | schemas | `billing."order"` | `postgresql://user:pass@host/dbname` |
| MySQL and MariaDB | databases | ``billing.`order` `` | `mysql://user:pass@host/dbname` |
| SQLite | nothing: it has a single namespace and ignores the list | `"order"` | the file in `introspection.providerConfig.sqlite.file` |
| SQL Server | schemas | `billing.[order]` | `mssql://user:pass@host:1433/dbname`, or [two other formats](/guides/connect-to-sql-server/#1-write-the-connection-string) |

## 2. Introspect the new database (if the schema differs)

Skip this step when the logical schema is identical and you only swap the engine package. The existing artifact is already valid, so go straight to step 3.

A different database instance may have different tables or columns. For that, run introspection against it. It regenerates the physical layer of the schema artifact:

<Tabs syncKey="engine">
  <TabItem label="PostgreSQL">

```bash
npx askdb introspect \
  --engine postgres \
  --url "postgresql://user:pass@host/dbname" \
  --out my-app.schema \
  --schema-id my-app
```

  </TabItem>
  <TabItem label="MySQL">

```bash
npx askdb introspect \
  --engine mysql \
  --url "mysql://user:pass@host/dbname" \
  --out my-app.schema \
  --schema-id my-app
```

For MySQL and MariaDB, the URL's database is the one introspected, and the prompt `ask()` sends lists its tables unqualified (`orders`). [Stable IDs](/reference/schema-artifact-format/#stable-ids) lists the namespace each engine writes. The URL must name that database: if the path has no database (`mysql://user:pass@host:3306`) and you don't list databases, introspection throws an error instead of writing an empty schema. To introspect several databases at once (MySQL's "schemas"), list them. Each database becomes its own namespace (`sales.orders`), listed qualified in the prompt, and foreign keys between listed databases are kept:

```ts
// askdb.config.ts
import { env } from "@askdb/config";

export default {
  introspection: {
    provider: "mysql",
    providerConfig: {
      mysql: { databaseUrl: env("DATABASE_URL") },
    },
    schemas: ["app", "sales", "analytics"],
  },
  // ...
};
```

A foreign key into a database that wasn't introspected has no target in the artifact. Introspection drops it with a `cross_database_fk` warning that names the constraint and the referenced database.

- **No database list.** The warning covers every foreign key into another database.
- **A database list.** It covers every foreign key into a database missing from the list.

The database list is the `schemas` setting in the config above.

  </TabItem>
  <TabItem label="SQLite">

For SQLite, set the file path via `introspection.providerConfig.sqlite.file` in `askdb.config.ts`:

```ts
// askdb.config.ts
export default {
  introspection: {
    provider: "sqlite",
    providerConfig: {
      sqlite: { file: "./my-database.db" },
    },
  },
  // ...
};
```

Then run:

```bash
npx askdb introspect --out my-app.schema --schema-id my-app
```

SQLite has no schemas, so its tables appear under the `public` namespace, in table ids like `table:public.orders`. The prompt `ask()` sends lists them unqualified (`orders`).

  </TabItem>
  <TabItem label="SQL Server">

```bash
npx askdb introspect \
  --engine sqlserver \
  --url "mssql://user:pass@host:1433/dbname" \
  --out my-app.schema \
  --schema-id my-app
```

SQL Server accepts three connection-string formats, and a server with a self-signed certificate needs a TLS option: see [Connect to SQL Server](/guides/connect-to-sql-server/).

  </TabItem>
</Tabs>

On Postgres and SQL Server, `introspection.schemas` lists schemas (the default is every non-system schema). On MySQL and MariaDB it lists databases, as above. SQLite has a single namespace and ignores it. `askdb introspect --schemas app,sales` does the same for one run and overrides the configured list.

The connection string format follows each engine's convention. The engine itself comes from `--engine` (or `introspection.provider` in `askdb.config.ts`) — the CLI does not infer it from the URL. The artifact records which engine produced it, and `askdb ask` infers the dialect from the artifact.

For one-off live introspection without installing `askdb` in the project, include the driver in the same ephemeral command:

```bash
pnpm dlx -p askdb -p mysql2 askdb introspect --engine mysql --url "$MYSQL_URL"
npx -p askdb -p mssql askdb introspect --engine sqlserver --url "$SQLSERVER_URL"
```

## 3. Update the `dialect` value in `ask()` calls

The schema artifact records which engine it was introspected from. The CLI (`askdb ask`) and `@askdb/client` use it to infer the dialect, so those entry points need no update. A `dialect` set in `askdb.config.ts` takes precedence over the artifact's engine: remove it, or change it, when you switch.

This holds for Prisma-introspected artifacts too. The connector reads the `datasource.provider` from your `.prisma` file and records it, so `askdb ask` knows the dialect without a live database. The mapping:

- `postgresql` becomes `postgres`.
- `mysql`, `sqlite` and `sqlserver` keep their names.
- So does `cockroachdb`.

When using `@askdb/client` with no `dialect` in the config, the dialect resolves from the schema artifact's recorded provider, the same inference the CLI uses. No code change is needed after a dialect switch if the new artifact declares the correct provider.

To force a specific dialect (for example, if the artifact's provider doesn't match your target engine), pass it as a per-call override:

```ts
// askdb initialized at startup with createAskDb() — see Embed in a Node app.
const { sql } = await askdb.ask(question, {
  dialect: "mysql",      // overrides auto-resolution
});
```

All six dialect specs ship inside `@askdb/core`. The dialect ids are:

- `postgres` and `cockroachdb`.
- `mysql` and `mariadb`.
- `sqlite` and `sqlserver`.

The engine packages (`@askdb/mysql`, `@askdb/postgres` and the rest) supply the *introspection* connector for that engine, and re-export its dialect constant for convenience. You need them to introspect, not to generate.

## 4. Update your driver

Swap the driver library for the one that matches the new engine. The execution layer is yours — AskDB doesn't open the connection — so this is a straight library swap.

<Tabs syncKey="engine">
  <TabItem label="PostgreSQL">

```ts
import { Pool } from "pg";

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  statement_timeout: 5000,
  max: 10,
});

const { rows } = await pool.query(sql);
```

  </TabItem>
  <TabItem label="MySQL">

```ts
import mysql from "mysql2/promise";

const pool = mysql.createPool({
  uri: process.env.MYSQL_URL,
  connectionLimit: 10,
});

const [rows] = await pool.execute(sql);
```

  </TabItem>
  <TabItem label="SQLite">

```ts
import Database from "better-sqlite3";

// Read-only, so a generated write fails.
const db = new Database(process.env.SQLITE_FILE ?? "./my-database.db", { readonly: true, fileMustExist: true });

const rows = db.prepare(sql).all();
```

  </TabItem>
  <TabItem label="SQL Server">

```ts
import mssql from "mssql";

// An ADO.NET string: mssql doesn't read mssql:// or sqlserver:// URLs.
const pool = await mssql.connect(process.env.SQLSERVER_URL);

const result = await pool.request().query(sql);
const rows = result.recordset;
```

The driver reads fewer connection-string formats than AskDB does. [Connect your own pool](/guides/connect-to-sql-server/#4-connect-your-own-pool) shows a config object that works in development and production.

  </TabItem>
</Tabs>

## On dialect parity

Postgres is the reference dialect — features ship there first and the other engines follow. For most analytical questions, the engines this guide covers generate equivalent SQL; for engine-specific features (JSON operators, window function syntax, regex variations), behavior follows what each engine supports natively.

If you hit a dialect difference that surprises you, that's a bug — file it on [the project issues](https://github.com/Ygilany/AskDB/issues).

## Running multiple engines side by side

Nothing stops you from querying two schema artifacts against different dialects in the same process. With `@askdb/client`, pass the schema and dialect as per-call overrides:

```ts
// askdb initialized at startup with createAskDb() — see Embed in a Node app.

const fromOrders = await askdb.ask(question, {
  schema: { path: "./orders.schema" },
  dialect: "postgres",
});

const fromAnalytics = await askdb.ask(question, {
  schema: { path: "./analytics.schema" },
  dialect: "mysql",
});
```
