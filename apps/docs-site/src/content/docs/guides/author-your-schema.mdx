<p class="doc-eyebrow">Schema author guide</p>

<p class="doc-lede">Raw introspection gives the model structure, which may be enough for simple schemas and simple queries. Enrichment is what gives it real meaning and context: descriptions, business concepts, and domain phrasing that make generation reliable.</p>

<Aside type="tip">Studio is the recommended way to enrich your schema: a local browser UI that edits your schema artifact directly. You can also edit the artifact's files by hand, in the [schema artifact format](/reference/schema-artifact-format/).</Aside>

## Before you start

Have a schema artifact on disk. If you haven't run introspection yet, the [Quickstart](/quickstart/) gets you to one in two commands.

## Enrich in Studio

Studio is the browser-based editor. Launch it from your project root:

```bash
npx askdb studio
```

The command opens the schema directory in `introspection.outputDir` from `askdb.config.ts`, or `./askdb/` when that isn't set. Pass `--schema <dir>` to open another directory for this run. By default Studio serves on `http://127.0.0.1:5556`; `studio.listen.port` and `studio.listen.host` change that. It reads and writes the files in your schema folder directly — no separate database, no separate copy of your schema.

Write descriptions in plain language, with the words your users say: AskDB folds them into the prompt next to the tables and columns they describe ([What the model actually receives](/concepts/the-schema-artifact/#what-the-model-actually-receives)). What you can edit, all of it optional:

- **Tables.** Per-table description, aliases (the names users actually use), and a "common query language" section that captures domain phrasing.
- **Columns.** Descriptions, enums, and sensitivity markers. Mark columns like `email`, `ssn`, or `internal_notes` as `sensitive` so the prompt-construction layer can tag or omit them — and so `validateSensitiveReferences` can flag any SQL that touches them before it runs. Sensitivity overrides are escalate-only: marking a table or column sensitive always takes effect, but "Not sensitive" can't un-mark something `schema.json` already marks sensitive.
- **Concepts.** Cross-table business concepts (`customer`, `active subscription`, `paid order`) that don't map to one table.
- **Tenant policy.** When your app is multi-tenant, declare tenant roots and scoped tables. See [Scope queries to a tenant](/guides/multi-tenancy/) for the full walkthrough.

Studio also offers AI-assisted drafts: describe a table or concept in plain language and Studio proposes a draft for your review. Suggestions are always confirmed by a human before they land in the artifact. See the [Studio tour](/studio/) for a view-by-view walkthrough.

If you work with a coding agent, give it the [askdb-enrich-schema skill](/skills/askdb-enrich-schema/SKILL.md): it asks you what ambiguous columns mean and writes your answers into `tables/*.md` and `concepts.md`.

## Example: extend the Quickstart's shop

The [Quickstart](/quickstart/)'s three tables need no enrichment, because the model answers from their column names alone. This example adds two tables whose meaning the names don't carry, then fixes a wrong answer with enrichment. Run it in the Quickstart's `askdb-shop` folder, with its SQLite `shop.db`. The dates are stored as text, so on the Quickstart's Postgres fallback the SQL the model writes differs from the SQL shown here.

### 1. Add plans and subscriptions

Create `extend-shop.sql`. It adds 2 plans and 5 subscriptions:

```sql title="extend-shop.sql"
CREATE TABLE plans (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  monthly_price NUMERIC(10, 2) NOT NULL
);
CREATE TABLE subscriptions (
  id INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL REFERENCES customers (id),
  plan_id INTEGER NOT NULL REFERENCES plans (id),
  status TEXT NOT NULL,
  started_at TEXT NOT NULL,
  ended_at TEXT
);
INSERT INTO plans VALUES (1, 'Basic', 9.00), (2, 'Pro', 29.00);
INSERT INTO subscriptions VALUES
  (1, 1, 2, 'A', '2026-01-05', NULL),
  (2, 2, 1, 'C', '2026-02-10', '2026-05-10'),
  (3, 3, 2, 'T', '2026-10-28', NULL),
  (4, 4, 1, 'P', '2026-04-20', NULL),
  (5, 4, 2, 'A', '2099-01-01', NULL);
```

`status` holds a one-letter code: `A` is active, `T` trial, `P` past due and `C` cancelled. Subscription 5 starts in 2099.

Create `extend-shop.mjs`, which loads the file into `shop.db`:

```js title="extend-shop.mjs"
import { readFileSync } from "node:fs";
import { DatabaseSync } from "node:sqlite";

new DatabaseSync("shop.db").exec(readFileSync("extend-shop.sql", "utf8"));
console.log("Added plans and subscriptions to shop.db");
```

Run it, then introspect again so the schema artifact has the new tables:

<Tabs syncKey="pkg">
  <TabItem label="npm">

```bash
node extend-shop.mjs
npx askdb introspect
```

  </TabItem>
  <TabItem label="pnpm">

```bash
node extend-shop.mjs
pnpm exec askdb introspect
```

  </TabItem>
  <TabItem label="yarn">

```bash
node extend-shop.mjs
yarn askdb introspect
```

  </TabItem>
</Tabs>

`askdb introspect` prints `Wrote askdb/schema.json: 5 tables (sqlite).`

### 2. Ask a question the names can't answer

Ask for the monthly recurring revenue, and pipe the SQL into the Quickstart's `run-query.mjs`:

```bash
npx askdb ask --question "What's our monthly recurring revenue from active subscriptions?" | node run-query.mjs
```

The model has only names and types to go on, so it guesses what "active" means:

```sql
SELECT SUM(plans.monthly_price) AS monthly_recurring_revenue
FROM subscriptions
JOIN plans ON subscriptions.plan_id = plans.id
WHERE subscriptions.status = 'active';
```

No row has the status `active`, so the sum is `null`.

### 3. Enrich the subscriptions table

The schema needs two things: what the `status` codes mean, and the rule for an active subscription. Codes alone aren't enough. With only those, the model writes `status = 'A'` and gets `58`: it counts subscription 5, which hasn't started, and leaves out subscription 4, which is past due but still active.

1. Run `npx askdb studio`, open **Tables** and select `subscriptions`.
2. On the **Enrichment** tab, under **Columns**, find `status`. Set its **Description** to `Subscription state, as a one-letter code: A = active, T = trial, P = past due, C = cancelled.`, and its **Enum notes** to `A, T, P, C`.
3. Under **Common Query Language**, put the business rules in **Business vocabulary**:

   ```text
   - An active subscription has status A or P (past due still counts), started_at on or before today, and ended_at NULL or after today. A trial (T) is not active.
   - MRR (monthly recurring revenue) is the sum of plans.monthly_price over active subscriptions.
   ```

4. Click **Save**.

Studio writes `askdb/tables/subscriptions.md`. To enrich without Studio, create the file yourself. This is what Studio writes, without the column entries it adds for the columns you left empty:

```markdown title="askdb/tables/subscriptions.md"
---
id: 'table:public.subscriptions'
name: subscriptions
schemaId: askdb
columns:
  - id: 'table:public.subscriptions#status'
    enum:
      - A
      - T
      - P
      - C
    description: >-
      Subscription state, as a one-letter code: A = active, T = trial, P = past
      due, C = cancelled.
---
# Table: subscriptions

## Common query language

- An active subscription has status A or P (past due still counts), started_at on or before today, and ended_at NULL or after today. A trial (T) is not active.
- MRR (monthly recurring revenue) is the sum of plans.monthly_price over active subscriptions.
```

A rule that spans several tables, such as *customer* in a schema with both `users` and `leads`, fits a concept in `concepts.md` instead.

### 4. Ask again

Run the same command. The model now applies the rule:

```sql
SELECT SUM(plans.monthly_price) AS mrr
FROM subscriptions
JOIN plans ON subscriptions.plan_id = plans.id
WHERE (subscriptions.status = 'A' OR subscriptions.status = 'P')
  AND subscriptions.started_at <= date('now')
  AND (subscriptions.ended_at IS NULL OR subscriptions.ended_at > date('now'));
```

The answer is `38`: Ada's Pro plan (29.00) and Margaret's past-due Basic plan (9.00). The model writes the SQL, so yours can differ in layout, but it should return the same answer.

## Re-introspecting

When your database schema changes (new columns, renamed tables, added relationships), re-run introspection. The physical layer (`schema.json`) is regenerated; your enrichment markdown (`tables/*.md`, `concepts.md`, `tenant-policy.md`) is preserved.

```bash
npx askdb introspect
```

With your introspection provider and URL configured in `askdb.config.ts` (and matching env vars in `.env`), no flags are needed. See the [Configuration reference](/reference/config/) for per-engine details.

A renamed table or column gets a new [ID](/reference/schema-artifact-format/#stable-ids), and its enrichment and sensitivity marks don't follow it. After a rename in the database:

1. Run `git diff schema.json` to see which IDs changed. Look for removed `"sensitive": true` lines too: re-introspection drops a mark on an ID that no longer exists, and doesn't warn about it.
2. In `tables/*.md`, change each `id` and `columns[].id` that names an old ID to the new one.
3. Put back the sensitivity marks you found in step 1, in `schema.json` or in the front-matter.
4. Check that nothing still names an old ID. Studio lists [loader warnings](/reference/schema-artifact-format/#loader-warnings) such as `orphaned_table_id` under **Settings → Schema Warnings**. In code, read `loadSchema(dir).warnings`.

## Bundling for distribution

When another service or build artifact needs the schema as a single file:

```bash
npx askdb bundle ./my-app.schema --out my-app.schema.bundle.json
```

The bundle file is the entire artifact in one JSON. Load it with `loadSchema` the same way as a directory.

`askdb bundle` checks the bundle with the loader `ask()` uses before it writes it, and exits `1` with the loader's error if the directory doesn't load. So a front-matter error fails the build, not the service, and a bundle it writes always loads.

## Commit it

The schema artifact is source code. Check it into the repo, review changes in PRs, deploy it alongside your app. The artifact is the single source of truth for what the model sees about your database.
