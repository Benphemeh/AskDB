Find the message you see, and follow its fix. Each entry says what the message means, then how to fix it, with rarer causes and details after. If yours isn't here, ask in a [Discussion](https://github.com/Ygilany/AskDB/discussions/categories/q-a).

Errors are grouped by where they appear:

| Group | What fails |
| --- | --- |
| [Config](#config) | No config found, a config with no `ai` block, a config that fails to load. |
| [Schema](#schema) | A schema path that is missing or unreadable, a `schema.json` that doesn't parse, an introspection that finds no tables. |
| [SQL generation](#sql-generation) | A declined question, a `SqlValidationError` rule, SQL that names a missing column or answers the wrong question. |
| [Model and API keys](#model-and-api-keys) | A missing API key or AI SDK package, a refused model call. |
| [Studio](#studio) | A missing driver, Studio execute off or unconfigured. |
| [SQL Server](#sql-server) | A self-signed certificate error. |
| [Tenant scope](#tenant-scope) | A `TenantScopeError`, a tenant policy that doesn't match the schema, a `TenantGuardrailError`, a `QueryParameterError`. |
| [RAG](#rag) | A retriever that is set but unused, retrieval that misses tables. |

## Config

### `No askdb.config.* or .config/askdb.* found in …`

The current working directory has no AskDB config. If the project has no config yet, create one with `npx askdb init`. If it has one, run the CLI from the directory that holds the config:

```bash
cd apps/api && npx askdb ask --question "..."
```

Details:

- **Where AskDB looks.** It looks for `askdb.config.<ext>`, then `.config/askdb.<ext>`, in the **current working directory only**. In a monorepo, it won't find a config in a parent directory.
- **Extensions, in precedence order.** AskDB tries `ts`, `mts` and `cts` first. Then it tries `js`, `mjs` and `cjs`.
- **Who prints it.** `askdb ask` and `askdb introspect` print this message. When you embed the libraries, `bootstrapAskDbEnv()` throws a similar error (`… found under <cwd>`).
- **When embedding the libraries,** the equivalent knob is the `cwd` option: `bootstrapAskDbEnv({ cwd: "/path/to/project" })`.

### `AskDB config at <path>: the config has no ai block`

The config file loaded, but it has no `ai` block, which every config needs. Add the provider and its connection, as [The `ai` block](/reference/config/#the-ai-block) shows. You need it even when you only run `askdb introspect`.

Two related errors:

- **No `introspection` block.** A config without one fails the same way, and the message names that block.
- **Other `AskDB config at <path>: …` errors** say what can't load. Examples are an unknown `rag.store`, a file with no default export, or top-level `await`, which the synchronous load can't run. Fix it in the file the message names.

### `Set ASKDB_DEBUG=1 to print the stack trace.`

The CLI hit an unexpected error, most often a config file that exists but fails to load. The line above the hint is the error message, and it usually names the file and line. Rerun with `ASKDB_DEBUG=1` to see the stack trace:

```bash
ASKDB_DEBUG=1 npx askdb ask --question "..."
```

Details:

- **Why a config fails to load.** The usual causes are a syntax error, a missing import, or dependencies that aren't installed yet.
- **Studio starts anyway.** `askdb studio` doesn't stop on a config that fails to load. It prints `askdb-studio: warning: <path> could not be loaded, so Studio is ignoring it: …` and starts without it. Fix the file and restart Studio. The setup wizard never overwrites it.

## Schema

### `Schema path not found.` / `ENOENT: no such file or directory`

Nothing exists at the schema path. A relative path is read from the current directory. Pass one of:

- A schema directory, such as `my-app.schema/`
- A bundle file from [`askdb bundle`](/reference/cli/#askdb-bundle)
- The `schema.json` inside a schema directory (the name matches in any case, so `Schema.json` works too)

Run `ls my-app.schema/` to check that `askdb introspect` wrote the directory. If it holds no `schema.json`, introspection didn't finish.

Which tool prints which message:

- **`askdb ask --schema`** prints `Schema path not found.`
- **`loadSchema()`** throws Node's `ENOENT: no such file or directory, stat '…'`.

### `Schema path is not readable (permission denied).`

`askdb ask` can't read the file at the schema path, or can't enter a directory above it. Check the owner and mode of the path and each directory on the way to it:

```bash
ls -ld my-app.schema my-app.schema/schema.json
```

The user that runs `askdb` needs read access to the files and execute access to every directory above them. When that user owns the directory, `chmod -R u+rX my-app.schema` grants both.

Two variations:

- **In a container,** the mounted schema directory must be readable by the container's user, which may not be yours.
- **A schema directory that exists but can't be listed** prints `Failed to parse schema.` instead, with `EACCES: permission denied, scandir '…'` after `Details:`. The same fix applies.

### `SchemaParseError: Refusing to load … as a standalone physical layer`

You passed a JSON file that isn't named `schema.json`, such as `prod-schema.json`, from a directory that holds other schema files. Loading the file alone would ignore those files, so AskDB refuses.

Pass the directory to `--schema` or `loadSchema()`, or rename the file to `schema.json`. To load only the physical layer, pass the file's content to `loadSchemaFromJson()`.

Details:

- **The other files.** They are `tenant-policy.md`, `tables/` and `concepts.md`. AskDB looks for them in any case, so a `Tenant-Policy.md` counts too.
- **Why AskDB refuses.** Loading the file alone, `ask()` would run without your tenant policy. It would also run without the `sensitive: true` marks in `tables/*.md`.

### `SchemaParseError: Schema directory … has a file name in the wrong case`

A file in the schema directory has the right name in the wrong case, such as `Tenant-Policy.md` or `tables/orders.MD`. Rename each file the error names, for example `git mv Tenant-Policy.md tenant-policy.md`.

Details:

- **Other examples** are `Concepts.md` and `Tables/`.
- **Both spellings.** The error can say `keep one of Tenant-Policy.md, tenant-policy.md`. Then the directory holds both spellings, which only a case-sensitive filesystem allows. Merge them into the correctly named file and delete the other, because a rename would overwrite it.
- **Why AskDB refuses on every OS.** AskDB reads these names exactly. On Linux, where file names are case-sensitive, it would skip the file. A skipped `tenant-policy.md` means `ask()` runs with no tenant policy. A skipped table file drops its `sensitive: true` marks. macOS and Windows would load the same directory, so AskDB refuses it on every OS, and you find out before you deploy.
- **`askdb bundle`** refuses the directory the same way.

### `Failed to parse schema.` / `SchemaParseError: Invalid schema.json at …`

`schema.json` doesn't have the shape AskDB reads. `askdb introspect` writes `schema.json`, so the usual cause is a hand edit or a merge.

Fix the field the message names. Or write the file again. `askdb introspect` won't overwrite a `schema.json` it can't read, so delete it first:

```bash
rm my-app.schema/schema.json
npx askdb introspect --out my-app.schema --schema-id my-app
```

Details:

- **What the message holds.** `askdb ask` prints `Failed to parse schema.`, followed by the loader's message after `Details:`. That message, `Invalid schema.json at <path>:`, lists each field that's missing or has the wrong type. It gives each field's `path`, such as `["schemaId"]`.
- **What `askdb introspect` prints** when it won't overwrite the file: `@askdb/introspect: invalid schema artifact file at …`.
- **What the rewrite keeps.** Your `tables/*.md`, `concepts.md` and `tenant-policy.md` stay as they are.

### `Failed to load schema.`

Reading the schema path failed with a file system error other than a missing path or a permission. Pass a schema directory, the `schema.json` inside one, or a bundle file from [`askdb bundle`](/reference/cli/#askdb-bundle).

Node's error follows `Details:`. The usual one is `ENOTDIR: not a directory`, which means a part of the path is a file, as in `my-app.schema/schema.json/tables`.

### `Refusing to write … outside the schema directory: "…" is a symbolic link`

A file AskDB writes in the schema directory is a symbolic link. Writing through it would change the file it points at, which can be outside the schema directory, so AskDB refuses. Replace the link with a regular file that holds the content you want, then run the command or save again.

The files AskDB writes there:

- `schema.json`, from `askdb introspect --out` or Studio's **Resync schema**
- A `tables/*.md` file, or `tables/` itself
- `concepts.md` and `tenant-policy.md`
- Studio's `playground-history.json`

Details:

- **Where a link comes from.** A repository can carry symbolic links, so this can come from a checkout.
- **The directory itself.** The schema directory itself can be a symbolic link.
- **A linked `.gitignore`** doesn't stop Studio. Studio skips adding `playground-history.json` there and still saves the history, so add that line yourself.

### `Introspection found no tables or views for schema "…"`

`askdb introspect`, or Studio's introspection, found nothing to write after filters, so it wrote nothing. Check, in this order:

1. **The connection names the right database.** A URL that points at an empty database gives this error, and so does a SQLite path to a file that exists but has no tables. A SQLite path to a file that doesn't exist fails earlier, with a different error.
2. **The schema or database holds tables or views.** A Postgres schema with only enums or sequences counts as empty, because the artifact describes tables and views.
3. **The filters match something.** The message names the `--schemas`, `--exclude-schemas` and `--tables` values it ran with. From a config, it names `introspection.schemas`. `--tables` patterns match `<schema>.<table>`, such as `public.orders*`.
4. **The database user can read the catalog.** A role without access to the tables' metadata sees none.

Details:

- **Exit status.** `askdb introspect` exits `1`, and Studio answers `422`.
- **Nothing changes on disk.** An artifact with no tables can't be loaded, so an existing `schema.json` stays as it was.

## SQL generation

### `AskDB can't answer this as a read-only query: …`

The model declined the question, and the rest of the message is its reason. Ask a question the schema can answer, as a read. A question that asks for a read and a change together is declined as a whole, so ask for the read part alone.

Details:

- **When AskDB declines.** It declines when the schema has nothing that answers the question, such as "What's the weather like?". It also declines when the question asks to change data, such as "delete all orders".
- **In code,** `ask()` throws `QuestionDeclinedError`, with the reason in `reason`.
- **In the HTTP API,** the answer is `422 question_declined`.

### `SqlValidationError: SQL_EMPTY`

The model didn't return SQL: its reply had none in it, such as a sentence explaining why it can't answer. Rephrase the question so the schema can answer it.

### `SqlValidationError: SQL_NOT_SELECT_OR_WITH`

The model wrote a statement that isn't a query, such as `INSERT` or `DROP`. AskDB returns only `SELECT` or `WITH … SELECT` statements. If you see this on read questions, the model may be misreading the schema. Check that your table and column descriptions don't imply write operations.

### `SqlValidationError: SQL_MULTI_STATEMENT`

The model wrote more than one statement. Ask for a single result, or split the question into two `ask()` calls.

On SQL Server, it also fires in two more cases. See [SQL Server statements](/reference/sql-checks/#sql-server-statements).

- **A second statement written without a `;`.**
- **Code SQL Server may split anywhere,** such as a non-breaking space or a bare `$` outside a string. The message names the character.

### `SqlValidationError: SQL_COMMENT` / `SQL_FORBIDDEN_KEYWORD` / `SQL_FORBIDDEN_FUNCTION`

The SQL has a comment, a forbidden keyword or a call to a blocked function. [Keywords and functions](/reference/sql-checks/#keywords-and-functions) lists them for each engine. If one fires on a legitimate query, file an issue with the question and schema excerpt.

Two details:

- **Keywords count only as whole, unquoted tokens.** A column like `deleted_at` or `"delete"` is fine. An unquoted column or alias named like a keyword, such as `update`, trips the check.
- **A `$N` parameter written against a word,** such as `$1INTO`, trips it too, where the SQL may be read as Postgres. Put a space after the parameter.

### `SqlValidationError: SQL_LOCKING_READ`

The SQL is a locking read, such as `FOR UPDATE` or a SQL Server lock hint like `WITH (UPDLOCK)`. AskDB returns plain reads only. If the question asks to lock or reserve rows, rephrase it as a plain read. Write any locking statement your application needs in your own code.

On SQL Server, it also fires on two kinds of name. Write such a name quoted, and qualified when it's the only thing inside parentheses. See [Locking reads](/reference/sql-checks/#locking-reads).

- **A name like a lock hint,** such as `rowlock`.
- **A name that isn't plain ASCII,** such as `Größe`.

### `SqlValidationError: SQL_UNICODE_ESCAPED_IDENTIFIER`

On Postgres or CockroachDB, the SQL uses a Unicode-escaped name such as `U&"set\005fconfig"`, which AskDB refuses rather than decode. AskDB never asks the model for this form. Write a name that isn't plain ASCII in plain double quotes (`"注文数"`). See [Forms the checks refuse to read](/reference/sql-checks/#forms-the-checks-refuse-to-read).

### `SqlValidationError: SQL_STRING_CONTINUATION`

The SQL continues an `E'…'` string on a later line, which Postgres reads differently from the checks. Join the parts with `||`, or write one literal. A plain `'…'` string continued on the next line passes. See [Forms the checks refuse to read](/reference/sql-checks/#forms-the-checks-refuse-to-read).

### `SqlValidationError: SQL_ESCAPED_BYTE_STRING`

The SQL has a `b'…'` byte string (lower-case `b`) with a backslash, or one continued on a later line, which CockroachDB reads differently from the checks. Write the bytes as a hex string cast to `bytea` (`'\x00'::bytea`). A `b'…'` string with no backslash, and a `B'…'` bit string, pass. See [Forms the checks refuse to read](/reference/sql-checks/#forms-the-checks-refuse-to-read).

### `SqlValidationError: SQL_UNTERMINATED`

A string, quoted name, dollar-quoted string or block comment never closes, so the check can't tell where the statement ends. On MySQL or MariaDB, check that the dialect's `backslashEscapes` matches the server: a mismatch also lets SQL through that the server reads differently. See [Match your server's string settings](/guides/match-server-string-settings/).

### Generated SQL references a column or table that doesn't exist

The model hallucinated an identifier that isn't in your schema. This is the most common failure mode. AskDB doesn't check generated identifiers against the schema, so your database reports these when you run the query.

**Fix:** Enrich the relevant tables in your schema artifact with plain-English descriptions. The more context the model has, the less it invents. Studio's enrichment views do this:

```bash
npx askdb studio
```

The column can exist in the database while the model keeps getting it wrong. Then check two things:

- `askdb introspect` has run again since the column was added.
- The column's description in the schema artifact isn't ambiguous.

### The SQL is syntactically valid but logically wrong

The SQL checks are heuristics, so they can't tell whether the query answers your question. The quality of answers depends almost entirely on how well the schema artifact describes your data.

What the checks cover: AskDB confirms the statement kind and blocks write keywords, locking reads and side-effecting functions. It doesn't check identifiers, and it can't verify that the query answers your question semantically.

Checklist:
1. Does the relevant table have a description? It's the first paragraph of the table's `tables/*.md` file, after its heading.
2. Do column names match how users phrase questions? Add `aliases` to the table or column in its `tables/*.md` file.
3. Does the question use your own terms, such as "active customer"? Explain them in the table file's `## Common query language` section, which the prompt shows. See [Body](/reference/schema-artifact-format/#body).
4. Try a more capable model. `gpt-4o` instead of `gpt-4o-mini` makes a meaningful difference on complex schemas.

## Model and API keys

### `… no AI API key configured`

The config names a provider but no API key for it, so `askdb ask` and `createAskDb()` stop before they call the model. Set the key your config reads. The config `askdb init` writes reads it from `OPENAI_API_KEY`, or your provider's variable, in `.env` or your shell. So run the command from the directory that holds `.env`.

Details:

- **Try it without a model.** To try the CLI without a model, pass `--mock-sql`, as the message says.
- **What the message names.** It starts with what was running, such as `NL→SQL generation:`. Then it names the key setting for each provider, such as `ai.providerConfig.openai.apiKey`.

### `Provider '<name>' requires the optional peer dependency @ai-sdk/<name>`

`@askdb/ai` loads your provider's AI SDK package when it first builds a model, and that package isn't installed. Install the one the message names, such as `npm i @ai-sdk/anthropic`. In a bundled app, see [Bundle an app that uses AskDB](/guides/bundle-your-app/).

### `SqlGenerationError: Model call failed: …`

The provider refused the model call. The rest of the message is the provider's own. `error.cause` is the AI SDK's `APICallError`, with the HTTP status in `statusCode`:

- **401 or 403:** the key is wrong or revoked, or belongs to another provider or project. Check the value your config reads for the key.
- **404:** the provider has no model by that name, or your account can't use it. The default OpenAI model is `gpt-4o-mini`. Set another in `ai.language.model`. The config `askdb init` writes reads it from `OPENAI_MODEL`. With `ask()`, pass another model instance.

See [Bring your own model](/guides/bring-your-own-model/) for each provider's settings.

## Studio

### Studio shows `pg missing` and an **Install pg** button

Studio's **Execute Query** runs the generated SQL with your engine's driver package, and that package isn't installed. Install the package the chip names in the project that holds the schema directory, and reload Studio. The chip then reads `pg ready`. Generating SQL in Studio does **not** require a driver. Only the Execute Query action does.

### `Studio execute is off.` / `No execute connection configured.`

Studio shows one of these in the Playground when **Execute Query** can't run:

- **`Studio execute is off.`** means `studio.execute.enabled` isn't `true`.
- **`No execute connection configured.`** means execution is on, but `studio.execute.databaseUrl` isn't set. For SQLite, the setting is `studio.execute.file`.

Set both in `askdb.config.ts`, and restart Studio. Studio runs the generated SQL on that connection, so give it a read-only database role. Studio resolves the execute connection in this order:

1. `studio.execute.databaseUrl` / `studio.execute.file`
2. The introspection connection for the same engine, only when `studio.execute.useIntrospectionConnection: true`

The provider comes from `studio.execute.provider`, or the active `introspection.provider` when it's a live engine. If both are set and the query still can't connect, check that the database is reachable from your machine.

See [Configuration — Studio execute](/reference/config/#studio-execute-configuration) for the full resolution order.

## Tenant scope

### `TenantScopeError: MISSING_SCOPE`

Your schema has a `tenant-policy.md` file, so AskDB requires a `tenantScope` on every `ask()` call. Pass one:

```ts
const { sql } = await ask({
  question,
  schema,
  model,
  dialect,
  tenantScope: {
    access: {
      kind: "ids",
      tenantRoot: "table:public.organizations",
      ids: [currentUser.orgId],
    },
  },
});
```

See [`TenantScope`](/reference/core-api/tenancy/#tenantscope) for the full scope shape.

### `TenantScopeError: UNKNOWN_TENANT_ROOT`

The `tenantRoot` in the scope doesn't match any root defined in `tenant-policy.md`. Check the `id:` field of each root in the policy file. The scope must use the same stable table ID, such as `table:public.organizations`.

### `TenantScopeError: SUBTREE_NOT_RESOLVABLE`

The scope uses `access.kind: "subtree"`, but `ask()` couldn't expand it into IDs per tenant root. Pass a `resolveTenantDescendants` callback that returns an object keyed by root table ID. Put the seeds and same-table descendants under the scope's `tenantRoot`, and each descendant root's IDs under that root: `{ "table:public.agencies": ["1"], "table:public.clients": ["5"] }`. Or send a `multi_root` access with each root's IDs already expanded.

The message says which of these went wrong:

- No `resolveTenantDescendants` callback was passed.
- The callback returned an array, the flat shape from before per-root IDs.
- It returned something other than a plain object.
- It returned a key that isn't a tenant root in the subtree.
- It returned a value that isn't an array of non-empty string IDs.
- It returned no IDs at all.

Details:

- **No fallback.** AskDB doesn't query your database to find descendants, and it won't fall back to the seed IDs alone.
- **Lower-level calls.** Calling `resolveTenantSql()`, `buildTenantPromptBlock()` or `bindPreparedQuery()` directly with an unexpanded subtree scope throws the same error. None of them walks the hierarchy. Expand the scope first with `expandTenantScope()`, or rebind through `askdb.bind()`, which does.

See [Hierarchical scope](/guides/tenant-hierarchy/).

### `TenantScopeError: UNRESOLVED_TENANT_PLACEHOLDER`

The SQL uses a `:tenant_<root>_ids` placeholder that the scope has no IDs for, so AskDB refuses to return it with the placeholder unfilled. Re-ask the question under the right scope.

Common causes:

- **The scope covers another root** than the one the SQL filters on. An example is a template stored under an agency scope, rebound under a client scope.
- **A covered root has `ids: []`.**
- **The placeholder is written in another casing** (`:TENANT_AGENCY_IDS`), or runs into the next word (`:tenant_agency_idsOR`).
- **The scope is `global`.** A `global` scope binds no IDs at all, so SQL under it must not use a tenant placeholder.
- **At rebind, the schema has no tenant policy.** A template with a placeholder then throws this too.

### `TenantScopeError: UNESCAPABLE_TENANT_ID`

AskDB was asked to inline a tenant ID as a literal, and the ID can't be inlined safely. It contains a backslash or a character outside printable ASCII, such as an accented letter, `¥` or CJK. Use the default `tenantSqlMode: "sql-params"`, which passes tenant IDs as driver parameters. Then run `sql` with `tenantParams`. Or run `unboundSql` with `params`. A rebind takes the same option.

Details:

- **Where it fires.** It fires under `tenantSqlMode: "sql-only"`. `ask()`, `bindPreparedQuery()` and `askdb.bind()` all refuse such an ID.
- **Why AskDB refuses.** Such a literal can read differently on the server. A backslash depends on its string settings. A non-ASCII character's bytes depend on the connection charset: `¥` is a backslash under `sjis`. So AskDB refuses it on every dialect instead of returning SQL whose tenant filter a server could read differently.

### `TenantScopeError: TENANT_SQL_MODE_REQUIRED`

`ask()` got a schema with a tenant policy and no `tenantSqlMode`, under a dialect whose markers AskDB doesn't know: a custom `AskDialect`. Set `tenantSqlMode: "sql-params"` if your driver binds `$1`-style markers. Or set `tenantSqlMode: "sql-only"` to get the tenant IDs inlined as escaped literals.

Details:

- **Why AskDB doesn't guess.** AskDB can't tell which parameter markers a custom dialect's driver takes. The default `$1, $2, …` would be read as money constants on SQL Server and filter to the wrong tenant.
- **Built-in dialects don't need it.** Neither do `DialectSpec`s under one, such as `{ ...POSTGRES_DIALECT, backslashEscapes: true }`.
- **An unknown mode gives the same error,** on any dialect. A `tenantSqlMode` that is neither `"sql-params"` nor `"sql-only"` throws it. Examples are a typo such as `"sql_only"`, or an empty string. AskDB refuses it rather than read it as either mode.

### Driver error: `there is no parameter $1` / `Too few parameter values` after upgrading

`ask()` binds tenant IDs through driver markers by default, and your code runs `result.sql` without them. Pass `result.tenantParams` with `result.sql`. Or run `result.unboundSql` with `result.params`. To keep inlined IDs, set `tenantSqlMode: "sql-only"`. See [Executing the result](/reference/core-api/ask/#executing-the-result).

Details:

- **What changed.** Early beta releases inlined the IDs: see [Run tenant-scoped SQL with its `tenantParams`](/reference/upgrade-notes/#run-tenant-scoped-sql-with-its-tenantparams). With a `tenantScope`, `result.sql` now holds a marker where the IDs used to be inlined. The marker is `$1`, `?` or `@p0`. The IDs are in `result.tenantParams`.
- **What fails.** Running `result.sql` without them fails at the driver, on MySQL as a syntax error. It never returns other tenants' rows.
- **A rebind does the same.** A rebind is a call to `bindPreparedQuery()` or `askdb.bind()`. Run its `sql` with its `tenantParams`. Or run its `unboundSql` with its `params`, or pass `tenantSqlMode: "sql-only"`.

### `SchemaParseError: Invalid tenant policy: roots … both map to the placeholder …`

Two roots in `tenant-policy.md` derive the same placeholder. Each root's IDs are bound through its own placeholder, so a shared one would bind one root's IDs where the other root's column is compared. Rename one of the two roots named in the message. If the fallback below collides, use a label with ASCII letters or digits. See the `label` row in the [field reference](/reference/tenant-policy/#field-reference).

Details:

- **How a placeholder is derived.** It is the label lowercased, with every run of characters other than ASCII letters and digits turned into `_`. So `Agency` and `agency` both give `:tenant_agency_ids`.
- **The fallback.** A label with no ASCII letter or digit (Cyrillic, CJK and so on) uses the root's table name instead. `Клиент` on `table:public.clients` gives `:tenant_clients_ids`. That fallback can still collide, for example when both table names are non-ASCII too, or when it meets another root's label.
- **Where it's rejected.** AskDB rejects the policy when it loads. `ask()` and `resolveTenantSql()` reject a policy built in code the same way, and Studio refuses to save it.

### `SchemaParseError: … the tenant policy doesn't match schema.json, and enforcement is strict`

`tenant-policy.md` has `enforcement: strict`, and it names a column or foreign-key ID that `schema.json` doesn't have, or its roots form a cycle. The usual cause is a column renamed in the database and then re-introspected. Update `tenant-policy.md` to match `schema.json`: the message lists every problem with its IDs. Until you do, the schema doesn't load anywhere, and a freshly started Studio can't open it either.

The other causes:

- **A loop.** A `hierarchy` or `parent` edge loops back.
- **An undeclared root.** The policy names a root that `roots` doesn't declare. It can be in `scopeThrough`, `hierarchy` or `parent`. It can also be in a polymorphic `mapping`.
- **A column on another table.** The field names a column that `schema.json` has on another table, such as a `scopeThrough` column of a different table. The message then says `column … is on <table>`.

Details:

- **Why the load fails.** A strict policy that doesn't match its schema fails the load instead of running tenant checks against the wrong columns.
- **A missing table doesn't fail it.** An entry for a table that `schema.json` doesn't have stays a warning in every mode.
- **`enforcement: warn` while you fix it.** It loads the schema with each problem in `schema.tenantPolicy.warnings`. But `warn` also returns SQL that fails the tenant check instead of throwing, so use it only while you fix the file.
- **`askdb introspect --out`** prints the same list after it writes.

See [When the policy and the schema disagree](/reference/tenant-policy/#when-the-policy-and-the-schema-disagree).

### `TenantGuardrailError`

Your tenant policy uses `enforcement: strict`, and the SQL failed the tenant check, so AskDB throws instead of returning it. Inspect the `warnings` array on the error to see which table and which rule triggered it ([`TenantGuardrailError` rules](/reference/core-api/errors/#tenantguardrailerror-rules)). Then re-ask the question or narrow it. [What the tenant check requires](/reference/tenant-policy/#what-the-tenant-check-requires) lists what passes.

The check is a heuristic: passing it doesn't prove the query is tenant-safe. So keep tenant isolation enforced in the database. See [Run generated SQL safely](/concepts/safety-boundaries/#run-generated-sql-safely).

Details:

- **Under a `subtree` scope,** each covered root the query reads needs its own placeholder. See [Hierarchical scope](/guides/tenant-hierarchy/).
- **At rebind.** `bindPreparedQuery()` and `askdb.bind()` run the same check on a stored template, under the scope you rebind with. With `enforcement: warn`, they refuse a failing template unless you pass `acceptWarnings: ["tenant"]`. The message says so.

### `QueryParameterError: DIALECT_SPEC_REQUIRED`

A rebind got a template whose dialect rules it can't recover, and no `dialect` in its `guardrails` argument. A rebind runs a stored template from an earlier `ask()` with new values, through `bindPreparedQuery()` or `askdb.bind()`. Pass the spec you gave `ask()` as `dialect`. If `ask()` ran with the built-in rules, the built-in id is enough, such as `dialect: "postgres"`.

The template is one of these:

- **One `ask()` made under your own `DialectSpec`.** Its `preparedQuery.dialectRules` is `"host"`.
- **One stored by a beta release without `dialectRules`.** See the [upgrade note](/reference/upgrade-notes/#update-your-bindpreparedquery-and-askdbbind-calls).
- **One from an app that loads two copies of `@askdb/core`,** such as ESM beside CJS. It gets `"host"` templates from the built-in constants of the other copy, and the same fix applies.

See [`bindPreparedQuery()`](/reference/core-api/rebind/#bindpreparedqueryprepared-values-guardrails).

### `QueryParameterError: MISSING_GUARDRAIL_CONTEXT`

`bindPreparedQuery()` was called with two arguments. It re-checks the stored template before binding, so it needs a third: `{ schema, tenantScope? }`, the same schema and the caller's scope you pass to `ask()`. With `@askdb/client`, call `askdb.bind(prepared, values, { tenantScope })` instead, which supplies the schema.

A `:tenant_*` key in the values throws `TENANT_VALUE_SUPPLIED`, because tenant IDs now come from `tenantScope`. See [`bindPreparedQuery()`](/reference/core-api/rebind/#bindpreparedqueryprepared-values-guardrails).

## RAG

### The retriever is set, but the prompt has the full schema

When `ask()` skips retrieval, it puts the full schema in the prompt instead. Pass a `logger` to see why: each skip logs `askdb.pipeline.retrieval.skipped` with a `reason`.

| `reason` | Why | Fix |
| --- | --- | --- |
| `below_threshold` | You passed a `totalSchemaChunkCount` at or below `retrievalThresholdChunks` (default 30). With the default, a schema of 30 chunks or fewer goes into the prompt whole. | None needed. To retrieve anyway, lower `retrievalThresholdChunks`. |
| `no_results` | The retriever found no chunks for the schema's `schemaId`: the index is empty, or you built it from a schema with another `schemaId`. | Build the index from the schema you pass to `ask()`. |
| `schema_not_v2` | The schema object isn't a schema artifact: it has no `schemaId`. | Load the schema with `loadSchema()`. |

```ts
import { createAskDbLogger } from "@askdb/core";
import { buildSchemaIndex, createMemoryStore } from "@askdb/rag";

const index = await buildSchemaIndex({ schema, embedder, store: createMemoryStore() });
const { sql } = await ask({
  question,
  schema,
  model,
  dialect: "postgres",
  retriever: index.retriever,
  totalSchemaChunkCount: index.stats.chunksTotal,
  logger: createAskDbLogger({ correlationId: "rag-check", level: "info" }),
});
```

### Retrieval misses the tables a question needs

The retriever returns the chunks nearest the question, `retrievalK` of them (default 8). The prompt holds only the tables those chunks point to. A table with no description looks far from every question, and a table the question reaches only through a join is the one most often missed. The model then guesses, and the SQL checks still pass.

To fix it:

1. Run `askdb rag query --question "<question>"` and find the table that's missing from the results.
2. Give that table a description, aliases and business context in its `tables/*.md` file. List the questions people ask in its `## Example questions` section.
3. If the question uses a term that spans tables, add a concept to `concepts.md` that links them. A retrieved concept brings every linked table into the prompt.
4. Run `askdb rag index` again, then the query.

Raising `retrievalK` also helps. [Check that retrieval finds every table](/guides/rag-for-large-schemas/#check-that-retrieval-finds-every-table) has a worked case, and [Find the right tables with RAG](/find-the-right-tables/) walks through it.
