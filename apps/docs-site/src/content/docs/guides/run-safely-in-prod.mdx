AskDB runs its SQL checks on the SQL before it's returned. Those checks catch common model mistakes, but they aren't a security boundary: your application and database own everything that depends on runtime context.

This page is the checklist for that side of the boundary, so that SQL which gets past the checks still can't write or read what it shouldn't. For what AskDB does and doesn't check, see [Safety boundaries](/concepts/safety-boundaries/).

## Before you start

- **A service that runs the SQL `ask()` returns.** AskDB returns SQL and never runs it, so every control below sits in your application or your database. [Embed in a Node app](/guides/embed-in-node/) sets one up.
- **Access to create a database role,** or the credentials of one that can only read.

## Database role

Connect under a role that <em>can't</em> write — even if AskDB's SQL checks miss something. This is the single most important defense.

<Tabs syncKey="engine">
  <TabItem label="PostgreSQL">

```sql
CREATE ROLE askdb_reader LOGIN PASSWORD '…';
GRANT CONNECT ON DATABASE myapp TO askdb_reader;
GRANT USAGE ON SCHEMA public TO askdb_reader;
-- Grant only the tables AskDB is meant to query. Leave sensitive tables out.
GRANT SELECT ON public.orders, public.customers TO askdb_reader;
-- Start every transaction this role opens as read-only.
ALTER ROLE askdb_reader SET default_transaction_read_only = on;
```

Table grants alone don't make a Postgres role read-only. Every role can still call some built-in functions that write, for example `lo_from_bytea`, which creates a large object. AskDB's function denylist blocks the known ones, but this role exists for SQL that gets past those checks. With `default_transaction_read_only` on, such a call fails with `cannot execute lo_from_bytea() in a read-only transaction`. The setting applies to new sessions of that role, and a session can change its own default, so also run each generated query inside a read-only transaction: `BEGIN READ ONLY` … `ROLLBACK`.

  </TabItem>
  <TabItem label="MySQL">

```sql
CREATE USER 'askdb_reader'@'%' IDENTIFIED BY '…';
-- Grant only the tables AskDB is meant to query. Leave sensitive tables out.
GRANT SELECT ON myapp.orders TO 'askdb_reader'@'%';
GRANT SELECT ON myapp.customers TO 'askdb_reader'@'%';
```

The same statements work on MariaDB. Also run each generated query inside a read-only transaction, `START TRANSACTION READ ONLY` … `ROLLBACK`, so a write that gets past AskDB's checks and the grants fails.

  </TabItem>
  <TabItem label="SQLite">

SQLite has no roles or grants. Open the database file read-only, so a generated write fails:

```ts
import Database from "better-sqlite3";

const db = new Database("./app.db", { readonly: true, fileMustExist: true });
```

A read-only handle still reads every table in the file. Keep tables AskDB mustn't query in another database file.

  </TabItem>
  <TabItem label="SQL Server">

```sql
CREATE LOGIN askdb_reader WITH PASSWORD = '…';
-- Then, in your application's database:
CREATE USER askdb_reader FOR LOGIN askdb_reader;
-- Grant only the tables AskDB is meant to query. Leave sensitive tables out.
GRANT SELECT ON dbo.orders TO askdb_reader;
GRANT SELECT ON dbo.customers TO askdb_reader;
```

SQL Server has no read-only transaction, and a driver such as `mssql` runs a whole batch. So the user's permissions are what stop a write that gets past AskDB's checks. Grant `SELECT` and nothing else: no `EXECUTE`, and no role such as `db_datawriter` or `db_owner`.

  </TabItem>
</Tabs>

Use that role's credentials in the connection string AskDB's consumers use. Don't reuse your application's admin user.

### System catalogs

On Postgres you can't take catalog read access away from a single role. `pg_catalog` and `information_schema` are readable through `PUBLIC`, which every role belongs to, so a `REVOKE … FROM askdb_reader` on them has no effect. Through the catalogs, `askdb_reader` can see the names and columns of every table in the database, view definitions, and function source code. It still can't read rows from a table it has no `SELECT` on.

If that metadata matters, pick one of these:

- **Accept catalog visibility.** Most deployments do. Keep the data itself out of reach with the table and column grants above, which the catalogs don't bypass.
- **Use a dedicated database.** Catalogs such as `pg_class` describe only the objects in the current database, so a database (for example a reporting copy) that holds only the tables AskDB may query shows only those tables. Cluster-wide catalogs such as `pg_roles` and `pg_database` still list every role and database.
- **Revoke from `PUBLIC`.** `REVOKE SELECT ON pg_catalog.pg_class, pg_catalog.pg_proc FROM PUBLIC;` blocks direct reads of those catalogs, but for every role in that database: your application, `psql`'s `\d`, and the role AskDB's introspection runs as lose them too, so grant them back to the roles that need them. It also doesn't hide everything: views such as `pg_tables`, casts such as `'public.secrets'::regclass`, and functions such as `pg_get_functiondef` still return catalog data. Test it against your own tooling before you rely on it.

## Connection limits

Set a statement timeout and a small pool. Generated SQL should be fast — a slow query is usually a sign of a malformed question or a missing index, not a real long-running report.

<Tabs syncKey="engine">
  <TabItem label="PostgreSQL">

```ts
import { Pool } from "pg";

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,
  statement_timeout: 5000,        // 5s — adjust to your workload
  idle_in_transaction_session_timeout: 5000,
});
// An idle client whose connection drops emits on the pool; without a listener, the process exits.
pool.on("error", (err) => console.error({ err }, "idle database client error"));
```

  </TabItem>
  <TabItem label="MySQL">

```ts
import mysql from "mysql2/promise";

const pool = mysql.createPool({ uri: process.env.DATABASE_URL, connectionLimit: 10 });

// The timeout is a session setting, so set it on the connection that runs the query.
// mysql2's types don't take unknown[], so params is any[].
async function runWithTimeout(sql: string, params: any[] = []) {
  const conn = await pool.getConnection();
  try {
    await conn.query("SET SESSION max_execution_time = 5000"); // ms, for SELECT; adjust to your workload
    const [rows] = await conn.execute(sql, params);
    return rows;
  } finally {
    conn.release();
  }
}
```

On MariaDB, the variable is `max_statement_time`, in seconds: `SET SESSION max_statement_time = 5`. [Embed in a Node app](/guides/embed-in-node/#3-run-the-sql-in-a-handler) shows a handler that sets it with the read-only transaction.

  </TabItem>
  <TabItem label="SQLite">

SQLite has no statement timeout, and `better-sqlite3` runs each query synchronously, so a slow generated query blocks the whole Node process until it finishes. Its `timeout` option only sets how long to wait for a locked database. Serve a shared service from a database server with a statement timeout.

  </TabItem>
  <TabItem label="SQL Server">

```ts
import mssql from "mssql";

const pool = await mssql.connect({
  server: process.env.DB_HOST ?? "localhost",
  database: process.env.DB_NAME,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  requestTimeout: 5000, // 5s — adjust to your workload
  pool: { max: 10 },
});
```

  </TabItem>
</Tabs>

## Row limits

The SQL `ask()` returns has no row limit, so a question like "show me every row in this 100M-row table" can load the whole table into your server and your UI. Cap the rows in your application: [Cap the rows a query returns](/guides/cap-the-rows-a-query-returns/) has a helper for each engine that keeps the query's `ORDER BY`.

## Audit logging

Log every question, every generated SQL string, the user who asked, and the outcome. Keep it in your existing logging system — AskDB doesn't log on your behalf.

```ts
import { createAskDbLogger } from "@askdb/core";
import { logger } from "./logger.js";

// askdb initialized at startup with createAskDb() — see Embed in a Node app.
const correlationId = crypto.randomUUID();
logger.info({ correlationId, userId, question }, "askdb.question");

try {
  // AskDB's own pipeline events, under the same correlation ID.
  const askdbLogger = createAskDbLogger({ correlationId, level: "info" });
  const { sql, tenantParams } = await askdb.ask(question, { logger: askdbLogger });
  logger.info({ correlationId, sql }, "askdb.generated");

  // runCapped: see Cap the rows a query returns.
  const { rows } = await runCapped(sql, tenantParams);
  logger.info({ correlationId, rowCount: rows.length }, "askdb.executed");
  return rows;
} catch (error) {
  logger.error({ correlationId, error }, "askdb.error");
  throw error;
}
```

`createAskDbLogger` writes AskDB's structured pipeline events as JSON to stderr, each tagged with the correlation ID; [`createAskDbLogger`](/reference/core-api/logging/#createaskdbloggeroptions) lists its options. To send them to your own Pino logger instead, pass that as `logger`: it fits `AskDbLogger`.

## Approval flows

For high-stakes questions — anything that touches sensitive data, or that runs against production reporting databases — show the SQL to a human before executing.

A common pattern:

1. Call `ask()` and return `{ sql }` (no execution).
2. Render the SQL in the UI with the question for context.
3. On user confirmation, POST the SQL back to a separate execution endpoint that runs it under the read-only role.

This works because AskDB returns checked SQL as a value — your application controls when, if, and how it runs.

## Sensitive columns

Mark sensitive tables and columns in the schema artifact, and decide whether the prompt tags them or leaves them out. [Keep sensitive columns out of prompts](/guides/keep-sensitive-columns-out-of-prompts/) covers marking them, the prompt setting, checking the SQL, the database role and the RAG index.

## Multi-tenancy

If your app is multi-tenant, make the database the tenant boundary: run generated SQL under Postgres row-level security keyed on a per-request setting, or your engine's equivalent. [Enforce tenancy in the database](/guides/enforce-tenancy-in-the-database/) covers the policies, the per-request transaction, and the checks that show the setup works.

On AskDB's side, declare tenant policy in the schema artifact and pass a `tenantScope` to every `ask()` call. AskDB prompts the model to filter by tenant, binds your tenant IDs, and runs the tenant check, a heuristic that looks for a tenant predicate on each scoped table. That check doesn't prove the query is scoped correctly. By default (`tenantSqlMode: "sql-params"`) the IDs are driver parameters, never part of the SQL text: run `result.sql` with `result.tenantParams`, or `result.unboundSql` with `result.params`. Keep that default in production. `sql-only` inlines the IDs as literals, for tools that take one SQL string. See [Multi-tenancy](/guides/multi-tenancy/).
