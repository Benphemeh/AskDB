The schema artifact is the folder of files your team authors, reviews, and checks into version control. It's the model's only source of knowledge about your database, and it's yours to evolve like any other piece of source code.

This page explains how the artifact is put together and why. The [Schema artifact format](/reference/schema-artifact-format/) lists every file and field.

## Two layers

The artifact keeps two kinds of knowledge apart, because they come from different places.

The **physical layer** is `schema.json`: the tables, columns, types, keys and relationships. It comes from the database. `askdb introspect` reads the database and writes it, and writes it again each time you run it. You rarely edit it by hand.

The **enrichment layer** is markdown: a file for each table you describe, plus optional business concepts and a tenant policy. It comes from people: what a table means, what your users call it, and how they phrase questions about it. Introspection never touches it.

<FileTree>

- askdb/
  - schema.json the physical layer, from the database
  - tables/
    - orders.md enrichment for one table you describe
    - users.md
  - concepts.md optional business concepts
  - tenant-policy.md optional tenant policy

</FileTree>

The split lets each layer change at its own pace. Re-introspection can't erase what your team wrote. And a diff of `schema.json` shows what changed in the database, and nothing else.

## Stable IDs join the layers

The markdown doesn't repeat table or column names. It refers to them by ID, such as `table:public.orders` or `table:public.orders#status`.

AskDB builds each ID from the names in the database, so the same database always gives the same IDs. That is what lets your markdown keep matching after every re-introspection.

The cost is renames. A renamed table or column gets a new ID, and AskDB can't tell a rename from a removal plus an addition. The markdown that named the old ID stops applying, and the loader reports it as a warning instead of guessing. [Enrich your schema](/guides/author-your-schema/#re-introspecting) has the steps to follow after a rename.

## Sensitivity only escalates

A table or column can be marked sensitive in `schema.json` or in its markdown. The two places aren't equal. Markdown can mark something sensitive, but it can't un-mark it. Only `schema.json` can.

This is deliberate. Markdown is the layer many people edit, often in [Studio](/studio/) (AskDB's browser UI for enriching a schema), so a mistake there is likely. A `sensitive: false` in markdown can't expose a column that `schema.json` marks sensitive. Un-marking takes a change to `schema.json`, which is a small, visible diff for a reviewer, and re-introspection keeps it.

The two layers check spelling differently. Take a typo in the key `sensitive`:

- **In markdown front matter** (the YAML block at the top of a markdown file), the loader refuses a key it doesn't know, so the typo fails the load.
- **In `schema.json`,** the loader ignores a key it doesn't know, because the file stays open to keys a newer AskDB adds. A misspelled `"sensitve": true` marks nothing. `loadSchema()` reports it as an `unknown_key` warning with the closest known key, and that warning is how you find out. [Loader warnings](/reference/schema-artifact-format/#loader-warnings) lists it.

## What the model actually receives

The model never sees the folder you author. It reads one schema text that AskDB builds from both layers at generation time. Take the `orders` table from the [Quickstart](/quickstart/)'s shop database, with an alias and a column description added in its markdown. The model reads it as a block like this:

```text title="One table in the schema text"
TABLE orders -- aliases: purchases
  - id INTEGER (PK NOT NULL)
  - customer_id INTEGER (NOT NULL)
  - product_id INTEGER (NOT NULL)
  - quantity INTEGER (NOT NULL)
  - ordered_at TEXT (NOT NULL) -- the date the customer placed the order
  FK (customer_id) -> customers (id)
  FK (product_id) -> products (id)
```

The structure comes from `schema.json`, and the comments come from your markdown. Each table is a block in a DDL-like form, with your enrichment folded in as inline comments. The comments carry the descriptions, aliases, column notes, "common query language" and business context, each next to the table or column it describes. Each table lists its foreign keys, and your concepts follow the tables.

Sensitive fields are tagged or withheld in this text, according to your [mode](/concepts/modes-and-dialects/#sensitive-fields) settings.

The prompt carries this text and the question. It never carries your rows, your credentials or your query results.

Two additions:

- **A schema with a tenant policy.** The prompt also carries a tenant policy block and the `context` from your `tenantScope`, as advisory text. The `tenantScope` is the caller's tenants, which your application passes on each call. The block names tenant IDs only by placeholder, such as `:tenant_agency_ids`, never by value. [Privacy model](/concepts/privacy-model/) has the full list of what reaches the model.
- **A schema too large to send whole.** AskDB renders only the slice retrieved for the question, in the same form. See [RAG for large schemas](/guides/rag-for-large-schemas/).

## Directory or bundle

You author the artifact as a folder, because a folder of small files diffs and reviews well. To ship it to a service, an agent or a build, `askdb bundle` packs the folder into one JSON file. It refuses a folder the loader refuses, and loading the bundle gives the same result as loading the folder.

The loader refuses a file name in the wrong case, such as `Tenant-Policy.md`, on every OS. Here is why. On Linux, where file names are case-sensitive, the loader would otherwise skip that file without a word, and a skipped `tenant-policy.md` turns tenant enforcement off. On macOS and Windows the same folder would load. Refusing everywhere makes the mistake fail on a laptop before it can fail open in production.

Whoever can write the artifact can change what AskDB loads and what the model sees. AskDB parses each part of it and puts it into the model prompt, so load schema files only from sources you trust. The parts are:

- `schema.json`
- `tables/*.md`
- `concepts.md`
- `tenant-policy.md`
- an inline `schemaJson`, in place of a folder or bundle

Schema front matter must be YAML, and AskDB refuses any other format.

## Why a file, not a prompt template

The schema artifact is a deliberate choice. The alternative, a prompt template buried in application code, is opaque, hard to review, and tangled with the rest of your codebase.

A versionable file means:

- Your data team can review changes in a PR like any other code.
- You can see, line by line, what context the model receives.
- Enrichment evolves at its own pace, decoupled from app deploys.
- The same artifact powers the CLI, the library, and the HTTP API: one source of truth.
