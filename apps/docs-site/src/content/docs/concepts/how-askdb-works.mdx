AskDB turns a question and a [schema artifact](/concepts/the-schema-artifact/) (the files that describe your database to the model) into checked SQL, and stops there. Your application decides whether to run that SQL, runs it, and keeps the audit trail.

<figure>

```diagram

# packages/core/src/ask.ts (maybeRetrieveDdl, generateSelectSqlForAsk, which builds the
# prompt, then enforceGuardrails).

lane askdb: AskDB

step generate @askdb: 4. generate
+ step provider @model: writes the SQL
step check @askdb: 5. check
step run @app: review, approve and run it under a read-only role
group `ask()`: retrieve prompt generate check
load -> retrieve
retrieve -> prompt
prompt -> generate
generate -> provider: prompt
provider ..> generate: SQL
generate -> check
check -> run: checked SQL
```

## The five steps

Take a question from the [Quickstart](/quickstart/): "How much has each customer spent in total, highest first?"

You call `ask()` from `@askdb/core` with that question, the loaded artifact, your model and the SQL dialect to write in:

```ts
import { ask } from "@askdb/core";

const result = await ask({
  question,
  schema,             // the artifact, from loadSchema()
  model,              // a Vercel AI SDK model
  dialect: "sqlite",
});
```

You get back one `SELECT` statement that has passed AskDB's checks, such as this one:

```sql
SELECT customers.name, SUM(products.price * orders.quantity) AS total_spent
FROM customers
JOIN orders ON customers.id = orders.customer_id
JOIN products ON orders.product_id = products.id
GROUP BY customers.id
ORDER BY total_spent DESC;
```

Between the question and that SQL, AskDB runs the steps in the diagram, in order. The CLI and the HTTP API run the same steps.

### 1. Load the schema artifact

AskDB writes SQL from your schema artifact, so the artifact has to be in memory first. Who loads it depends on how you call AskDB:

- **The CLI, the HTTP API and `@askdb/client`** load it for you, from a directory, a bundle file or a `schema.json`.
- **When you call `ask()` directly,** you load it with `loadSchema()` and pass it in.

### 2. Retrieve relevant chunks (optional)

Some schemas are too large for one prompt. For those, you pass a [retriever](/guides/rag-for-large-schemas/), a search over the artifact's chunks: the small pieces it's split into for indexing. AskDB then sends the model only the chunks that match the question. Without a retriever, this step does nothing and the model gets the whole artifact.

Two details:

- The retriever comes from `@askdb/rag`.
- A small schema can skip retrieval even with a retriever. To allow that, also pass the artifact's chunk count. At or below `retrievalThresholdChunks` chunks, 30 by default, AskDB uses the whole artifact.

### 3. Build the prompt

AskDB assembles what the model reads: your question, the schema text, and the SQL dialect to write in.

Some artifacts have a [tenant policy](/concepts/tenant-isolation/), a file that says which tables belong to a tenant and which column filters them. For those, the prompt also holds the policy. Your application passes the caller's tenant scope with each call, to say whose data the caller may see. The prompt holds the scope's context, such as the caller's role, as advisory text. [Privacy model](/concepts/privacy-model/#what-the-model-sees) lists everything the prompt holds.

### 4. Generate

AskDB sends the prompt to the model you supplied, and the model returns SQL. Any provider that works with the [Vercel AI SDK](/guides/bring-your-own-model/) will do. AskDB does not host inference: your key, your billing.

Sometimes the model declines instead, with a one-line reason. It does that in two cases:

- The schema can't answer the question.
- The question asks to change data. A question that mixes a read with a change is declined as a whole.

`ask()` then throws [`QuestionDeclinedError`](/reference/core-api/errors/#errors) before any check runs.

### 5. Check

A model can return SQL that you didn't ask for, so AskDB checks the SQL before it hands it to you. There are three checks:

- **The read-only check** looks for one statement that only reads, and refuses SQL that isn't.
- **The tenant check** runs when your artifact has a tenant policy. It looks for a tenant filter on each tenant-scoped table, and refuses or reports SQL that lacks one.
- **The sensitive check** runs when your artifact marks tables or columns `sensitive`. It reports SQL that reads one, or refuses it when you set it to strict. You mark one with `sensitive: true` in the artifact ([Sensitivity rules](/reference/schema-artifact-format/#sensitivity-rules)).

The checks catch common model mistakes, but they can miss things, so they aren't a security boundary. [SQL checks](/reference/sql-checks/) gives each check's rules, and [Safety boundaries](/concepts/safety-boundaries/) lists what they miss.

`ask()` then returns three things: the checked SQL, the values to bind when the SQL has parameters, and what the checks found. [`AskPipelineResult`](/reference/core-api/ask/#result--askpipelineresult) lists every field. What happens next is your call.

## The runtime boundary

AskDB stops at checked SQL, and your application owns everything after it. "Your application" is the code that imports `@askdb/core` or calls the HTTP API. It owns:

- The database driver and connection pool.
- Read-only roles, and tenant isolation such as Postgres row-level security ([Enforce tenancy in the database](/guides/enforce-tenancy-in-the-database/)).
- Query timeouts, row limits, and result pagination. The SQL comes back without a row limit, and [Cap the rows a query returns](/guides/cap-the-rows-a-query-returns/) shows how to cap it on each engine.
- Whether to show the SQL to the user, log it, queue it for review, or run it immediately.
- Audit logging and observability.

This split is intentional. AskDB is a code-generation step, not a runtime, so it slots into the services and the security model you already have. Generated SQL can do only what its database role allows, and that's the role you already trust to run queries.

## Where the model lives

You bring the model. AskDB calls the provider you wire in, through the Vercel AI SDK, with your API key. Requests go straight from your environment to the provider. AskDB does not proxy, log, or cache them.

That model never sees your database connection, your credentials, or the rows your application returns. [Privacy model](/concepts/privacy-model/) has the precise list of what crosses the boundary.

## After the rows: a chart

AskDB has one optional step after your application runs the SQL: it can suggest a chart for the result. The experimental `@askdb/client/charts` entry point asks your model which chart fits, and returns a chart spec. The model picks from the question, the SQL and the column kinds, such as date, measure or category. Your application draws the chart from its own rows, with its own charting library, so the rows still never reach the model. See [Chart planning](/concepts/chart-planning/).
